## 1. 背景与目标

### 1.1 背景

使用者是**汽车配件供应商（Tier）的销售小组成员，共 4-6 人**。日常工作围绕「配套项目」展开：为主机厂或一级供应商提供零部件，项目从询价一路推进到定点、试产、量产供货、回款。

当前管理方式为 **Excel / 在线表格 + 微信 + 纸质本子**，存在以下具体问题：

| 编号 | 问题 | 后果 |
| --- | --- | --- |
| P1 | 项目进度只在自己表格里，同事之间互相不知道对方在跟什么 | 客户撞车、信息重复问、商机流失 |
| P2 | 阶段划分靠个人习惯，同一阶段不同人叫法不同 | 无法横向汇总，无法交接 |
| P3 | 每个阶段要记的信息不同（询价阶段记报价有效期，试产阶段记试装日期），Excel 只能堆列 | 表格又宽又空，难用难维护 |
| P4 | 阶段被客户打回、或自己填错要后退，无法留痕 | 事后扯不清责任和原因 |
| P5 | 换设备要重新找人要最新版表格 | 数据不同步、易丢 |

### 1.2 目标

1. **进度透明**：全组在一个看板上看到所有项目的当前位置与停滞情况。
2. **流程统一且可自定义**：阶段划分由业务自己定义（不改代码），全组共用一套。
3. **阶段信息结构化**：每个阶段能配置自己需要的字段，填不全不允许推进。
4. **回退可追溯**：任何后退都有原因、有人、有时间。
5. **零成本、多端可用**：不花钱，手机浏览器/主屏图标即可用；同一账号在 PC 与手机之间数据自动同步，且用户随时能判断"自己看到的是不是最新的"。

### 1.3 非目标（明确不做）

- 不做审批流，不做主管 / 经理视角，不做客户可见。
- 不存储任何机密信息：**报价单、图纸、样件照片一律不入库，且产品不提供金额字段**（见 R-02）。
- 不做评论、即时通讯、@提醒。
- 不做后端服务、数据库服务、不做任何付费依赖。
- 不做移动端原生 App（走 PWA）。

## 3. 名词定义

> 本章为强制约定，后续开发、沟通统一用此术语。

| 术语 | 英文 / 字段 | 定义 |
| --- | --- | --- |
| 客户 | Customer | 主机厂、一级供应商、经销商等往来单位。**长期资产**，一个客户下可有多个项目。 |
| 项目 | Project | 一个具体的配套供货业务，如"长城 H6 前保险杠"。**短期战役**，必须归属一个客户。 |
| 流程模板 | Flow Template | 一套节点定义，描述项目要经过哪些阶段、每个阶段有哪些字段。全局唯一，带版本号。 |
| 节点 | Node | 流程模板中的一个阶段，如"询价/报价"。 |
| 节点字段 | Field | 挂载在节点上的自定义字段，如"报价有效期"。 |
| 流转 | Advance | 项目从当前节点前进到下一节点。 |
| 回退 | Rollback | 项目从当前节点后退到之前的任一节点，**必须填原因**。 |
| 流程快照 | Flow Snapshot | 项目创建时对流程模板做的**深拷贝**，用于隔离后续模板变更。 |
| 停滞 | Stale | 项目在当前节点停留的天数超过节点配置阈值。 |

### 客户与项目的层级关系（重要决策）

**结论：采用两层结构（客户 → 项目）。**

理由：
1. 一个主机厂客户的合作周期通常是数年，而单个配套项目周期为 1-2 年。二者生命周期量级不同，混为一层会导致同一客户被重复录入数十次。
2. 客户维度需要独立信息（客户类型、合作状态、由谁负责、历史项目数），这些信息在单一层级下无处安放。
3. BRD 中的"开发新客户"被误列为节点。**它不是交付节点，而是销售活动**，与"询价→送样→定点"不在同一维度。本 PRD 中它被处理为：客户对象的 `status = developing`（开发中），而非项目节点。

**为了不增加录入负担**：新建项目时允许直接输入客户名称，若不存在则**自动创建客户档案**，不强制用户先去建客户。

## 4. 业务流程

### 4.1 默认流程模板（业务确认的 7 个阶段）

| 序号 | 节点名称 | 典型业务动作 |
| --- | --- | --- |
| 1 | 询价/报价 | 客户发 RFQ，我方出报价单 |
| 2 | 送样/打样 | 提交样件，客户试验认可 |
| 3 | 定点/立项 | 正式拿到项目 |
| 4 | 小批量试产/PPAP | 装配试装、量产件批准 |
| 5 | 量产供货 | SOP 后持续接单、发货 |
| 6 | 对账/开票/回款 | 对账、开票、催收 |
| 7 | 已关闭 | 项目结束（正常结束或丢单） |

> 该模板为**初始默认值**，落地后由业务在"流程模板配置"中自行调整。

### 4.2 正向流转

```
[询价/报价] → [送样/打样] → [定点/立项] → [试产/PPAP] → [量产供货] → [对账/回款] → [已关闭]
```

- 只允许逐节点向前，**不允许跳节点**。
- 推进前校验：当前节点所有 `required` 字段必须已填。
- 每次推进写入一条节点记录，并更新项目当前节点指针。

### 4.3 回退

- 可从当前节点回退到**之前任意一个节点**（不允许向前跳）。
- **强制填写回退原因**，原因不可为空。
- 回退类型（二选一，业务已确认需要区分）：
  - `customer_reject` 客户打回来了
  - `self_error` 我们自己填错了
- 回退**不删除**已填内容，原节点记录保留在历史中。
- 回退写入独立的回退历史表，记录：时间、操作人、从哪退到哪、原因、类型。

### 4.4 状态机

| 项目状态 | 说明 |
| --- | --- |
| `active` | 进行中 |
| `closed_won` | 成交关闭 |
| `closed_lost` | 丢单关闭 |

项目进入"已关闭"节点时，状态置为关闭态，从看板主视图移出（可在筛选后查看）。

## 5. 功能需求

优先级定义：**P0** = 第一版必须交付；**P1** = 紧随其后；**P2** = 远期。

### 5.1 P0 — 基础能力

#### FR-01 连接与授权（fine-grained PAT）

> v1.4 变更：原方案「GitHub Device Flow」已实测确认不可行（OAuth 端点不允许浏览器跨域），改为用户自行生成 fine-grained PAT 并粘贴。详见 7.2。

- 用户在 GitHub 生成 fine-grained PAT（仅授权数据仓库的 Contents 读写），粘贴进工具。
- 数据仓库以**粘贴地址**的方式录入（接受 `https://github.com/owner/repo`、`git@github.com:owner/repo.git`、`owner/repo` 等形态），由工具自动拆分 `owner` 与 `repo`；`branch` 可选。
- 工具需校验：Token 是否有效、仓库是否可访问、当前账号是否有写权限。
- 凭证（Token、仓库配置、账号信息）缓存到浏览器本地，之后免配置。
- 提供"退出登录"入口，清除本地凭证。

**连错仓库的防护（v1.5 新增，这是本产品最隐蔽的风险）**

`owner` 是仓库地址的前半段。若用户抄错，而错的地址恰好指向**另一个真实存在的仓库**，GitHub **不会返回任何错误**，工具会把数据静默写入该仓库。因此需要四道防护：

| 防护 | 要求 |
| --- | --- |
| 地址录入 | 只提供单个「仓库地址」输入框，自动拆分 owner / repo；无法解析时禁止提交并给出明确提示。**不提供**需要用户手填 owner 的独立字段 |
| 当前仓库可见 | 顶栏常驻展示当前 `owner/repo`，不使用悬浮提示承载（移动端无悬浮）。异常时转为告警样式 |
| 结构校验 | 读取远端 `config.json` 后校验其是否符合本工具结构（含 `flowTemplates` 且节点非空）。不符时给出"可能连错仓库"告警，并**阻止初始化**以避免覆盖他人文件 |
| 空仓库确认 | 远端已有文件但不存在 `config.json` 时，初始化前展示已有文件数量并要求二次确认 |
| 公开仓库 | 仓库为 public 时，在**所有页面**顶部展示醒目告警（不得只在设置页展示） |
| 失败诊断 | 仓库不可访问时，必须能区分「仓库不存在」「Token 未覆盖该仓库」「Token 权限不足」三种成因，并列出当前 Token 可访问的仓库中名字相近者，用于定位拼写错误与 owner 填错 |

**验收标准**
1. 未连接时访问任意业务页，跳转到连接页。
2. 粘贴完整仓库地址能正确拆出 owner 与 repo；无法解析的输入被拒绝且禁止提交。
3. Token 无效、仓库不存在、无写权限三种情况分别给出可区分的错误提示。
4. 顶栏在任何页面都能看到当前 `owner/repo`。
5. 远端 `config.json` 结构不符时，全站出现告警，且**不存在**可点的初始化入口。
6. 远端有文件但无 `config.json` 时，初始化按钮改为需要二次确认的文案，并显示已有文件数量。
7. 仓库为 public 时，进站即出现告警（不必进入设置页）。
8. 连接成功后能读到数据仓库内容。
9. 刷新页面后无需重新配置。
10. 退出登录后本地凭证被清除，且接口请求不再携带 Token。
11. 连接失败（404）时**自动触发诊断**，明确指出 Token 可访问的仓库清单中是否包含目标仓库，并列出名字相近的仓库；不得只给出"可能是私有仓库"这类无法行动的建议。

#### FR-02 首次初始化

- 当数据仓库为空时，引导用户"初始化"，写入默认流程模板 + 空客户/项目集合。
- 组内第一个人初始化即可，后续成员直接使用。

**验收标准**：初始化后看板可正常渲染，默认 7 个节点按顺序展示为列。

#### FR-03 客户管理

- 字段：客户名称（必填、组内唯一）、简称、类型（主机厂 / 一级供应商 / 经销商 / 其他）、状态（开发中 / 合作中 / 暂停 / 已终止）、负责销售、备注。
- 支持列表查看、搜索（按名称/简称）、新建、编辑。
- 客户详情页展示该客户下的全部项目及各自所处节点。

**验收标准**
1. 客户名称重复时给出提示并阻止保存。
2. 客户详情页能正确列出其名下项目数量与列表。
3. 新建项目时输入不存在的客户名，自动创建客户并建立关联。

#### FR-04 项目管理

- 项目字段：项目名称/编号（必填）、所属客户（必填）、负责销售（默认当前用户）、当前节点（只读，由流转驱动）、下次跟进日期、备注。
- 支持新建、编辑、查看、关闭。
- 支持按客户、负责销售、节点、关键字筛选。

**验收标准**
1. 项目创建时自动绑定当前流程模板的**快照**与版本号。
2. 列表/看板能按负责销售和节点筛选。
3. 项目被关闭后不再出现在看板主视图。

#### FR-05 项目详情

展示五个区块：
1. **流转轨迹条**：以线性 SVG 图直观展示已完成节点、当前节点与后续节点，回退路径单独标注（详见 FR-24）。
2. **基本信息**：名称、客户、负责销售、创建时间、当前节点。
3. **当前节点信息**：当前节点需填写的字段表单。
4. **流转历史**：按时间倒序列出所有节点进出记录与已填字段值。
5. **回退历史**：时间、操作人、起止节点、原因、类型。

**验收标准**
1. 历史记录完整可读，字段值按填写时的值原样展示（不因字段定义变化而丢失）。
2. 流转轨迹条与流转历史、回退历史的展示内容一致，不出现互相矛盾。

#### FR-06 节点流转（正向推进）

- 项目详情页提供"推进到下一节点"按钮。
- 点击后：
  1. 校验当前节点所有必填字段；
  2. 校验不通过则定位到缺失字段并提示，**不允许推进**；
  3. 通过则关闭当前节点记录（写入 `leftAt` / `leftBy`），创建下一节点记录，更新当前节点指针。

**验收标准**
1. 必填字段为空时，按钮点击无效并给出明确提示（指出哪个字段没填）。
2. 推进后看板中该卡片移动到下一列。
3. 流转历史新增一条记录，且携带本次填写的字段值。

#### FR-07 节点回退

- 项目详情页提供"回退"按钮，弹出面板选择目标节点 + 回退类型 + 填写原因。
- 原因为空时不可提交。
- 提交后：当前节点记录标记为已回退，目标节点重新激活，回退历史新增一条记录。

**验收标准**
1. 目标节点列表只包含当前节点之前的节点。
2. 原因输入框为空时提交按钮禁用。
3. 回退后已填内容不被清空，仅重新进入该节点继续编辑。
4. 回退历史可查，且包含操作人、时间、起止节点、原因、类型。

#### FR-08 流程模板配置（自定义节点）

- 支持新增节点、重命名节点、删除节点、上下调整顺序。
- 每个节点可配置：名称、停滞阈值天数（超过则标红）、字段列表。
- 修改后生成**新的模板版本号**。
- **变更隔离（已确认）**：模板变更**不影响**已存在的项目。老项目继续按自己创建时的快照运行。
- **实时预览图**：配置区旁固定展示当前模板的线性流程图，任何编辑（增删节点、改名、调整顺序、增删字段）**立即反映到预览图**，无需先保存。渲染约定与 FR-24 一致。

**验收标准**
1. 仅模板管理员可进入配置页（非管理员看不到入口）。
2. 调整节点顺序后，新项目按新顺序流转。
3. 修改模板后，已存在项目的节点顺序、字段定义**完全不变**。
4. 模板配置每次保存产生一次提交记录，可追溯历史版本。
5. 编辑节点名称或调整顺序时，预览图在 **300ms 内**更新，且与实际节点顺序一致。
6. 预览图**不触发任何写请求**，纯本地渲染。

#### FR-09 自定义字段

支持的字段类型：

| 类型 | 说明 | 校验 |
| --- | --- | --- |
| `text` | 单行文本 | 可选最大长度 |
| `textarea` | 多行文本 | 可选最大长度 |
| `number` | 数字 | 数值范围 |
| `date` | 日期 | 日期选择器 |
| `select` | 单选下拉 | 选项值必填 |

**明确不支持金额类型**（已决策 2026-09-29，见 R-02）。字段类型固定为上述 5 种，无 `currency`。

字段级配置项：名称、类型、是否必填、默认值、是否启用。

**验收标准**
1. 模板中配置的字段，在项目详情对应节点自动渲染为对应控件。
2. 标记为必填的字段未填写时，无法推进到下一节点。
3. 字段值以键值对形式随节点记录一并持久化。
4. 所有 `textarea` 字段输入框下方固定展示提示文案："请勿填写报价金额、客户联系人等敏感信息——数据将对全组可见且永久留存。"

#### FR-10 看板视图（主视图）

- 横向按节点分列，纵向堆叠项目卡片。
- 卡片展示：项目名称、客户简称、负责销售头像、停滞天数。
- 支持拖拽卡片到相邻列完成推进（拖拽时同样执行必填校验）。
- 停滞超过阈值的卡片标红。
- 支持按负责销售、客户筛选。

**验收标准**
1. 拖拽到下一列等价于点击"推进"，校验逻辑一致。
2. 拖拽跨多列或向前拖拽时被拒绝并复位。
3. 移动端看板可横向滚动，卡片可点开详情。

#### FR-11 列表视图

- 表格形式展示项目，列支持排序与筛选，作为看板的补充视图。
- 提供与看板的一键切换。

**验收标准**：切换视图后筛选条件保持不变。

#### FR-12 全组可见

- 所有登录成员默认可见全组全部客户与项目（已确认：先做全组可见）。

**验收标准**：任何成员登录后看到的数据集合一致。

#### FR-13 响应式布局

- PC 与手机浏览器共用同一网址，自适应布局。

**验收标准**：iPhone / Android 主流尺寸下无横向溢出，核心操作（推进、回退、填字段）可正常完成。

#### FR-14 多端同步与刷新触发

定义数据在"**何时**"重新拉取。同步采用**增量比对**：一次 Git Trees 请求取回全目录 sha，与本地缓存比对后只拉取发生变化的文件，无变化时零额外请求。完整策略见 7.9。

| 触发 | 动作 |
| --- | --- |
| 应用启动、进入列表页或项目详情页 | 增量同步 |
| 窗口重新获得焦点、`visibilitychange` 转为可见 | 增量同步（移动端从后台切回时最关键） |
| 用户手动点击刷新 | 强制全量比对 |
| 本地写入成功后 | 用响应返回的新 `sha` 更新缓存，**不得立即回读** |
| 定时轮询 | **不做** |

**验收标准**
1. A 设备保存后，B 设备切回标签页或重新进入页面，**无需手动操作**即可看到最新数据。
2. 数据无变化时，一次同步仅产生 1 次请求，其余走 304。
3. 手机切到后台再切回（Safari 可能已冻结页面），数据自动校验并刷新。
4. 写入成功后立即读取自己刚写的内容，不会读到旧版本。

#### FR-15 同步状态指示器

在全局固定位置展示同步状态，让用户随时判断数据新鲜度。

- 展示"最后同步：x 分钟前"，超过阈值（建议 10 分钟）转为警示色。
- 同步进行中展示进行中状态；同步失败展示失败状态。
- 提供手动刷新入口。
- 离线时明确标识"离线，当前为本地缓存"。

**验收标准**
1. 任一页面都能看到最后同步时间。
2. 进行中、成功、失败、离线四种状态可区分。
3. 离线提示不影响已填写内容的保留。

#### FR-16 写入冲突处理

GitHub 的写入粒度是**整个文件**，因此两人修改同一项目的**不同字段**（A 改备注、B 改下次跟进日期）同样会冲突。GitHub 不做字段级合并，字段级 diff 必须在**应用层**实现。

保存因 `sha` 过期返回 409 时：

1. **保留用户本地已填内容**，不刷新页面、不丢弃输入；
2. 自动拉取该项目最新版本；
3. 展示差异摘要，例如："张三 10:23 把节点从『送样/打样』推进到『定点/立项』，并填写了『定点日期』"；
4. 提供两个选项：
   - **基于最新版本重新提交我的修改**（保留双方在不同字段上的改动）；
   - **放弃我的修改，查看最新版本**；
5. 同一字段双方都改过时，**单独标出并由用户逐字段选择**，绝不自动覆盖。

**验收标准**
1. 409 发生后，用户已填写的字段**一个都不丢**。
2. 差异摘要准确指出变更人、变更时间与变更内容。
3. 同一字段的双边修改必须由用户显式选择，不存在静默覆盖。
4. 不存在"提示用户刷新后重试"这类会丢数据的兜底话术。

#### FR-17 离线可用与草稿补交

- 通过 Service Worker 缓存应用壳，断网时仍能打开并使用工具。
- 断网状态下允许编辑，修改暂存为**本地草稿**（IndexedDB），界面明确标识"未提交"。
- 恢复网络后主动提示："有 N 条未提交的修改，是否立即提交？"
- 草稿在提交成功前**不因刷新或关闭页面而丢失**。
- 同一项目仅保留最新一份草稿，再次编辑时覆盖上一份未提交草稿（不引入草稿历史，避免复杂度失控）。

**验收标准**
1. 断网后刷新页面，工具仍能打开并渲染缓存数据。
2. 断网时填写字段并保存，内容被保留为草稿且标识清晰。
3. 恢复网络后能一键提交草稿；提交成功后标识消除，遇冲突则走 FR-16。
4. 仍处于离线状态时提交草稿不丢失草稿，仅提示稍后重试。

> 依赖说明：FR-17 的"Service Worker 缓存应用壳"与 FR-21 的"PWA 安装"共用同一个 manifest，但交付节奏独立——离线能力属 P0（写入链路必须一次设计到位，后补需重构），安装体验属 P1。

**验收标准**
1. 待办页按紧急度排序（超期红 > 今日到期 > 手动待办）。
2. 点击待办可跳转到对应项目详情。

**验收标准**：能直观看出各项目的排期与耗时分布。

#### FR-24 流转轨迹条（可视化流转路径）

在项目详情页用一条**线性 SVG 轨迹条**，直观表达"当前在哪、走过哪些、接下来去哪、是否被退回"。这是本产品唯一需要图形绘制的核心视图。

**布局示意**

```
✓ 询价/报价 ──── ● 送样/打样 ──── ○ 定点/立项 ──── ○ 试产/PPAP ──── ○ 量产供货
        \\____ 红色反向流动虚线（回退路径，标注原因）____/
```

**节点与连线状态**

| 状态 | 视觉表现 |
| --- | --- |
| 已完成节点 | 实心、主题色、带勾选标记；其右侧连线为静态实线 |
| 当前节点 | 高亮描边 + 轻微呼吸动效；其右侧连线为**流动**虚线 |
| 未到达节点 | 灰度、空心；连线为静态灰线 |
| 被回退过的节点 | 保留已完成样式，额外叠加回退标记 |
| 回退路径 | 由当前节点指向目标节点的**红色反向流动**虚线，附回退类型与原因摘要 |

**渲染约定（FR-08 的预览图同样适用）**

1. **零依赖**：纯手写 SVG + CSS，不引入任何图布局库（理由见 7.8）。
2. **有限动效**：动画播放有限次数后趋于静止，**不做无限循环**。多卡片同时常驻动画会导致移动端掉帧。
3. **动效克制**：同一视图内**只让当前活跃的那一条边流动**，历史边与未来边一律静态。信息价值集中在"当前"。
4. **尊重系统偏好**：响应 `prefers-reduced-motion`，为 `reduce` 时全部动画退化为静态，且不增加额外交互开关。
5. **数据自足**：只读取项目自身数据（`flowSnapshot` + `nodeRecords` + `rollbackHistory`），不额外拉取模板配置。

**验收标准**
1. 轨迹条的节点顺序与项目 `flowSnapshot` **完全一致**，而非当前最新模板。
2. 当前节点、已完成节点、未到达节点三种状态视觉可区分。
3. 存在回退记录时，回退路径可见且可展开查看原因、类型与操作人。
4. 系统开启 `prefers-reduced-motion: reduce` 时无任何动画，信息仍完整可读。
5. 移动端可横向滚动；节点数达到 12 个时不溢出、不错乱。
6. 渲染轨迹条不产生任何 GitHub API 请求。

## 6. 数据模型

### 6.1 仓库文件结构

```
data-repo/                     (private 仓库)
├─ config.json                 流程模板、成员与管理员名单（全局单文件）
├─ customers/
│  ├─ cus_k3m9x2.json          一个客户一个文件
│  ├─ cus_p7q4r1.json
│  └─ ...
└─ projects/
   ├─ prj_20260929_a1b2c3.json 一个项目一个文件
   ├─ prj_20260929_d4e5f6.json
   └─ ...
```

**关键设计：一个业务对象一个文件（客户、项目均是）。**

原因：GitHub 内容 API 的**写入单位为整个文件**，若同类对象共用一个大文件，4-6 人任何一次修改都会互相覆盖。拆分为单文件后，不同人改不同对象 = 不同文件 = 不同提交，天然无冲突。

**这条原则必须贯彻到所有集合型数据。** 反例：若客户集合共用一个 `customers.json`，则 A 录"长城"、B 录"吉利"会必然冲突——而录入新客户是销售最高频的动作之一，冲突不会是"很少发生"。

> 例外：`config.json` 是全局单文件，但**只有管理员会写**，冲突面收敛到 1 人，可接受。

### 6.5 编号规则

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 项目 | `prj_` + `YYYYMMDD` + `_` + 6 位随机串 | `prj_20260929_a1b2c3` |
| 客户 | `cus_` + 6 位随机串 | `cus_k3m9x2` |
| 节点 | `n` + 序号 | `n1` |
| 字段 | `f` + 序号 | `f1` |

> 项目与客户由**多端各自生成**，因此**不得使用自增序号**（跨设备必然碰撞），统一使用随机串。节点与字段位于 `config.json` 内、只有管理员写入，可用序号。

### 6.6 乐观锁

所有文件通过 GitHub 内容 API 更新时需携带当前文件的 `sha`。若 `sha` 与服务端不一致（他人已提交），接口返回 **409 Conflict**。

**冲突后的处理不是"提示刷新后重试"**——那会丢弃用户已填的全部内容。完整策略见 **7.9.3**，核心是：保留本地输入 + 展示差异摘要 + 由用户选择重新提交或放弃。

注意写入粒度是**整个文件**：两人修改同一项目的不同字段同样会冲突。字段级合并只能在应用层实现，GitHub 不做 merge。

业务已确认"各管各的项目，冲突很少"，因此不引入 OT / CRDT 等协同算法。但"几乎不冲突"与"冲突了不能丢数据"是两件事，后者必须做到。

## 7. 技术方案

### 7.1 架构总览

```
┌─────────────────────────────────────────────┐
│  Vue3 + Vite + Tailwind CSS (纯前端 SPA)     │
│  ├─ 视图层：看板 / 列表 / 项目详情 / 模板配置  │
│  ├─ 状态层：本地缓存 (IndexedDB) 优先渲染     │
│  └─ 数据层：GitHub REST API 客户端            │
└───────────────────┬─────────────────────────┘
                    │ HTTPS
        ┌───────────┴───────────┐
        │                       │
┌───────▼────────┐   ┌──────────▼──────────┐
│ GitHub Pages   │   │ GitHub 私有数据仓库  │
│ 托管前端静态资源 │   │ config/customers/    │
│ (public 仓库)   │   │ projects/*.json      │
└────────────────┘   └─────────────────────┘
```

**关键点：前端站点与数据仓库是两个独立仓库。** 前端资源走 Pages 公开分发（工具本身无秘密），数据存 private 仓库且**不经过 Pages**，仅由浏览器携 token 通过 API 读写。因此 GitHub Free 账号即可满足零成本要求。

### 7.2 认证：fine-grained PAT（v1.4 由 Device Flow 变更）

**变更原因（已实测 + 查证）**：GitHub 的 OAuth 端点 `/login/device/code` 与 `/login/oauth/access_token` 位于 `github.com/login/*`，**不返回任何 CORS 响应头**，浏览器无法跨域调用；这是 GitHub 的刻意设计（业界需要 Gatekeeper 一类代理才能绕开）。因此在纯前端架构下，标准 OAuth 与 Device Flow **都不可实现**。

实测对照：

| 端点 | `Access-Control-Allow-Origin` |
| --- | --- |
| `api.github.com/*` | `*`（并暴露 `ETag`，预检允许 `Authorization` / `If-None-Match`） |
| `github.com/login/device/code` | **无** |
| `github.com/login/oauth/access_token` | **无** |

**采用方案：用户在 GitHub 自行生成 fine-grained PAT，粘贴到工具中。**

界面需给出明确引导：
1. 选 **Fine-grained token**（不是 classic）；
2. **Repository access** → Only select repositories → 只勾选数据仓库；
3. **Permissions → Repository permissions → Contents** → Read and write；
4. 有效期按团队安全策略设置。

**这不是妥协，权限反而更小**：
- Device Flow 需要 `repo` scope，等于**可读写该账号下全部仓库**；fine-grained PAT 可精确到「单个仓库 + 仅 Contents」，**权限范围严格更小**。
- 无需注册 OAuth App、无需维护 `client_id`、不引入任何第三方依赖。
- 代价：每人手动配置一次（4-6 人属一次性成本），以及需要关注 Token 有效期（见 R-09）。

> **P1 备选增强**：若将来愿意引入一个免费 Serverless 代理（如 Cloudflare Worker）转发那两个请求，即可恢复"输 8 位码"的 Device Flow 体验。**数据层与 UI 层无需改动，只需替换"获取 Token"这一步**，因此不阻塞 v0.1。

### 7.3 数据读写策略

**读取（列表/看板加载）**

1. 用 Git Trees API（`recursive=1`）**一次请求**取回 `customers/` 与 `projects/` 下所有文件的 sha 列表。
2. 与本地缓存的 sha 比对，**只拉取有变化的文件**。
3. 单文件读取使用条件请求（`If-None-Match`）。GitHub 对 304 响应**不计入速率限制**，因此重复打开工具几乎零消耗。

> 本节只定义"**怎么读**"。至于"**何时**触发读取"、"冲突了怎么办"、"断网了怎么办"，统一见 **7.9 同步与一致性策略**，不在其他章节另立规则。

**写入（保存项目）**

1. 取文件当前 sha；
2. `PUT /repos/{owner}/{repo}/contents/{path}` 携带 base64 内容与 sha；
3. 成功后更新本地缓存 sha。

**速率限制评估**：认证用户 5000 请求/小时。4-6 人规模、配合 304 缓存，远低于上限。

**数据容量**：GitHub 内容 API 单文件 ≤ 1MB 可正常读取，本项目单文件为 KB 级，无风险。

### 7.4 路由

使用 **hash 模式**（`createWebHashHistory`）。GitHub Pages 无服务端重写能力，history 模式下刷新子路由会 404，hash 模式可完全规避。

### 7.5 本地缓存

- 使用 IndexedDB（或 localStorage）缓存最近一次拉取的全量数据，实现**秒开**与弱网可用。
- 缓存键为文件路径，值为 `{ sha, content, fetchedAt }`。
- 应用壳所需的静态资源由 Service Worker 管理，使断网时仍能打开工具。
- 离线/命中缓存时明确提示"数据可能不是最新"，并展示最后同步时间。
- 缓存的刷新触发点与失效规则统一由 7.9 定义，不在其他章节另设规则。

### 7.6 部署

- 前端仓库设为 **public**，通过 GitHub Actions（`actions/deploy-pages`）将 `dist/` 发布到 Pages。
- Vite 需配置 `base` 为仓库路径（如 `/pm-tools/`）。
- 数据仓库设为 **private**，将 4-6 名成员添加为 collaborator（Write 权限）。

### 7.8 图形渲染方案：为什么不用图布局库

FR-24 的流转轨迹条与 FR-08 的实时预览图都需要绘制节点与连线。可选方案包括 Vue Flow（`@vue-flow/core`）、AntV X6、D3 等图布局库，**本项目明确不采用，改为手写 SVG。**

**理由**

1. **拓扑是单链，不是网。** 4.2 规定流程只允许逐节点向前、不允许跳节点；回退是线性上的向后跳转。整个拓扑恒为**单链（linear chain）**，不存在分支、并行、汇合。图布局引擎的核心价值——求解带环 DAG 布局、正交路由避让、自动避让重叠——在本项目**完全用不到**。
2. **单链布局可常量时间手算。** 线性节点的坐标就是 `x = i × spacing`，连线是最简单的水平路径，不需要任何布局算法。
3. **零成本是硬约束。** 引入图库会明显增加产物体积与运行时开销，与"GitHub Pages 静态托管 + 零成本"的定位冲突。
4. **动效可控性更好。** 手写 SVG 时，"有限动效""只让当前活跃边流动""按边粒度控制"这些纪律可以精确实现；图库的动画通常是全局属性，难以按边约束。
5. **与产品语义不冲突。** 看板的本质是"一个阶段装 N 张卡片"，而流程图是"一个节点只画一次"。轨迹条被限定在**单个项目**的上下文里，天然只有一个节点实例，不存在把看板塞进流程图的语义错位。

**升级触发条件（重要）**

一旦业务提出下列任一需求，本决策即失效，需重新评估引入图布局库：

- 节点之间出现**分支**（一个节点流向多个后继节点）；
- 出现**并行**阶段（多个节点可同时进行）；
- 出现**汇合**（多个节点汇聚到一个节点）；
- 出现**非线性回环**（例如"试产不通过直接跳回送样"，与当前"回退到任意前置节点"仍属线性的定义不同）。

届时优先选 **Vue Flow**（Vue 3 原生、支持自定义节点组件与 `animated` 边）；若需要更强的正交路由与自动布局，再考虑 **AntV X6**。

**结论**：现在手写 SVG，**不要提前引入图库**。把省下的复杂度留给数据同步与冲突处理——那才是本项目的真实风险（见第 10 章）。

### 7.9 同步与一致性策略

多端同步是本产品的核心需求（BRD 明确要求）。它的难点**不在"怎么拉数据"，而在"何时拉、冲突怎么办、断网怎么办"**。本节是这三个问题的唯一权威定义。

#### 7.9.1 同步模型

**无服务端推送，采用"焦点驱动 + 增量比对"的拉取式同步。**

一次增量同步的成本：

1. 1 次 Git Trees 请求（`recursive=1`）取回 `config.json`、`customers/` 与 `projects/` 的全部 sha；
2. 与本地缓存的 sha 逐项比对，只对发生变化的文件发起读取；
3. 单文件读取走条件请求，命中 304 不计入速率限制。

因此"**数据没变化时的同步成本 = 1 次请求**"。这使高频触发（切换页面、切回焦点）在经济上完全可行。

**明确不做定时轮询**：移动端耗电、无后端推不了消息，且焦点驱动已覆盖绝大多数真实场景。

#### 7.9.2 触发时机

| 触发 | 动作 | 优先级 |
| --- | --- | --- |
| 应用启动 | 增量同步 | P0 |
| 进入列表页 / 项目详情页 | 增量同步 | P0 |
| 窗口重新获得焦点、`visibilitychange` 转为可见 | 增量同步 | P0 |
| 用户点击刷新 | 强制全量比对（忽略本地 sha） | P0 |
| 本地写入成功后 | 用响应返回的新 `sha` 更新缓存，**不得立即回读** | P0 |
| 定时轮询 | 不做 | - |

**为什么"不得立即回读"**：写入成功后立刻读取，有概率拿到尚未更新的内容。写入响应本身已包含新 `sha`，直接用它更新本地缓存即可——既避免不一致，也省掉一次请求。

#### 7.9.3 冲突处理

**写入粒度是整个文件**，这是 GitHub 内容 API 的硬约束。由此推出：

- 两人修改**不同项目** → 不同文件 → 无冲突；
- 两人修改**同一项目的不同字段** → 同一文件 → **依然冲突**；
- GitHub **不会**做字段级合并。字段级 diff 必须在应用层用"本地版本 vs 远端版本"两份 JSON 自行计算。

冲突（409）后的处理流程：

1. **保留用户本地已填内容**，不刷新页面、不丢弃输入；
2. 拉取该项目最新版本；
3. 生成差异摘要：变更人、变更时间、变更内容（节点推进 / 字段填写 / 回退）；
4. 用户二选一：
   - **基于最新版本重新提交我的修改**：以远端为基线叠加本地改动，并逐字段检测双边冲突；
   - **放弃我的修改，查看最新版本**；
5. 同一字段双方都改过时，**单独标出并由用户逐字段选择**，绝不自动覆盖。

> 因为"各管各的项目、冲突很少"，不需要 OT / CRDT 之类协同算法。但"几乎不冲突"和"冲突了不能丢数据"是两件事，后者必须做到。

#### 7.9.4 离线与草稿

| 能力 | 方案 |
| --- | --- |
| 断网可打开 | Service Worker 缓存应用壳 |
| 断网可读 | IndexedDB 缓存全量数据 |
| 断网可写 | 修改暂存为本地草稿，界面标识"未提交" |
| 恢复网络 | 主动提示"有 N 条未提交的修改"，一键提交；遇冲突走 7.9.3 |
| 草稿粒度 | 同一项目仅保留最新一份，不引入草稿历史 |
| 草稿生命周期 | 不因刷新或关闭页面而丢失，直至提交成功 |

#### 7.9.5 已知的同步局限

| 局限 | 影响 | 说明 |
| --- | --- | --- |
| 无实时推送 | 同事的改动需等本端触发同步才能看到 | 焦点驱动已覆盖绝大多数场景；不接受定时轮询的耗电代价 |
| 多标签页 | 同一浏览器两个标签各自持有独立内存状态 | 以页面重新获得焦点时同步为准；不引入 BroadcastChannel 跨标签通信（收益低于复杂度） |
| 客户端时钟不可靠 | 多端 `createdAt` 可能错乱 | **排序与"先后"判断一律以 GitHub 提交顺序为权威**，客户端时间仅用于展示 |
| ID 碰撞 | 多端各自生成 ID，理论上有极小碰撞概率 | ID 用日期 + 随机串（见 6.5）；碰撞时以远端已有文件为准并提示重建 |
| 授权次数 | Device Flow 的 token 存在各浏览器中 | 授权次数 = 人数 × 设备数；清缓存或隐私模式需重新授权，属预期行为 |

## 8. 权限模型

**必须明确：本产品不存在真正的权限隔离。**

原因：纯前端架构下所有数据都下载到浏览器，token 也保存在浏览器中。任何组员只要打开开发者工具，即可读取数据仓库的全部内容。模板配置的"仅管理员可见"**只是界面层面的隐藏**，不是安全边界。

因此权限按以下方式处理：

| 能力 | Member | Admin | 说明 |
| --- | --- | --- | --- |
| 查看全部客户与项目 | 是 | 是 | 全组可见 |
| 新建/编辑客户与项目 | 是 | 是 | |
| 推进/回退节点 | 是 | 是 | |
| 编辑流程模板 | 否（界面隐藏） | 是 | **软权限**，不构成安全防护 |

**管理员推荐方案（业务已授权由本 PRD 决定）**：**仅 1 人（你本人）为管理员**。

理由：
1. 模板是全组共用的全局定义，任何人可改会导致流程被随意改动而无人察觉。
2. 业务已确认"模板变更不影响老项目"，说明模板变更是**有长期副作用的操作**，更应收权。
3. 管理员名单写在 `config.json` 的 `admins` 字段中，需要变更时由管理员本人提交修改。

**同时必须承认**：由于不存在真实权限，任何成员理论上都可以直接修改 `config.json` 自行提权。这是零成本纯前端方案的固有代价，记录于 R-01。

| **R-06** | **强依赖 GitHub 可用性** | 中 | GitHub 故障或 API 变更将导致工具不可用。缓解：本地缓存保证只读可用；数据格式为纯 JSON，可随时迁出。 |
| **R-07** | **无审计合规能力** | 低 | 提交历史可追溯"谁改了什么"，但不满足正式审计要求。 |
| **R-08** | **文件附件不支持** | 低 | 业务明确报价单/图纸/样件照片为机密信息，不入库。工具内不提供附件上传。 |

## 13. 验收标准汇总

产品整体验收需同时满足：

1. **零成本**：全链路不产生任何费用（GitHub Free 账号即可运行）。
2. **多人同步**：A 电脑新建项目，B 手机打开后可见，无需手动同步。
3. **自定义闭环**：不修改任何代码，业务可自行新增一个节点、配置字段、并让新项目按新流程流转。
4. **模板隔离**：修改模板后，已存在项目的节点与字段定义零变化。
5. **强制校验**：必填字段未填时，看板拖拽与按钮推进均被阻止。
6. **回退留痕**：任一节点回退都能查到操作人、时间、起止节点、原因、类型。
7. **移动可用**：手机上可完成查看看板、推进节点、填写字段、回退四项操作。
8. **多端一致**：同一账号在 PC 与手机看到的数据完全一致。
9. **动效克制**：开启 `prefers-reduced-motion` 后全部动画消失且信息不丢失；产品内不存在无限循环动画。
10. **零绘图依赖**：图形相关功能（轨迹条、模板预览）不依赖任何图布局库。
11. **同步可感知**：任何页面都能看到最后同步时间；手机改完在 PC 上切回页面即可看到最新数据，无需手动刷新。
12. **冲突不丢数据**：保存遇到冲突时，已填字段一个不丢，且用户能看到对方改了什么。
13. **断网不白填**：断网时可打开工具、可编辑，修改不因刷新或关闭页面而丢失。
